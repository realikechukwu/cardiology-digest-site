The problem

Clinicians can't read 20 journals a week. Most of what gets published isn't for them anyway.

Each week, the top cardiology journals and the big general medical journals publish hundreds of items. Many are editorials, letters, errata and protocols. The few trials and meta-analyses that matter get lost among them. The digest separates the two, then writes up the studies worth reading so a busy clinician can get through them in about five minutes.

The method

Six stages, from PubMed to inbox

A GitHub Actions workflow runs every Sunday at 07:00 UTC. It is written in Python. Each stage is a small, testable step, and the pipeline's memory is a few JSON files under version control instead of a database. Select a stage to see how it works.

fetch_cardiology_pubmed.py

Query PubMed through NCBI E-utilities

Every run makes two searches over the last 7 days:

  • 17 specialty journals (Circulation, JACC, European Heart Journal, JAMA Cardiology, Heart Rhythm and others), all of whose content is included.
  • 3 general journals (NEJM, The Lancet, Nature), limited to cardiology through MeSH terms or title/abstract keywords.

The title/abstract fallback matters. Newly published and ahead-of-print papers often haven't been MeSH-indexed yet, so a MeSH-only search would quietly miss the newest and most important trials.

Records are fetched in batches with efetch, and the XML is parsed into title, abstract, authors, journal, date and publication types.

# Generated query for general journals

classify_article()

Sort by evidence type, not by keyword

Each article is classified from its PubMed publication types, the structured labels that NLM indexers assign. The rules are explicit and deterministic:

  • Excluded if any type is non-substantive, or if the title shows it is a protocol paper.
  • Priority if it is original research or a review and has an abstract.
  • Standard for everything else that has an abstract.

These rules run before any model is called, so the LLM never sees editorials or letters. That saves money and leaves less room for the model to go wrong.

state/seen_pmids.json · state/sent_pmids.json

Never send the same paper twice

PubMed records reappear as they move from ahead-of-print to issue publication, and the 7-day window can overlap between runs. To guarantee no repeats, every PMID is tracked in two JSON files kept in git:

  • seen: written after a successful fetch.
  • sent: written only after the email has actually been delivered.

After each run the workflow commits the updated files back to the repository. That gives an audit trail of what went out and when, and if a send fails partway, rerunning the job is safe.

# .github/workflows/weekly_digest.yml (excerpt)
on:
  schedule:
    - cron: "0 7 * * 0"   # Sundays 07:00 UTC
  workflow_dispatch: {}

concurrency:
  group: weekly-medical-digest
  cancel-in-progress: false

# …each specialty runs in turn, then:
github-actions[bot]
  "Update sent PMIDs after weekly digest"
select_for_summary()

Put the strongest evidence first

Each issue has a fixed budget of full summaries (10 by default). Papers are ranked by evidence weight before that budget is spent:

  • 1. RCTs, meta-analyses, systematic reviews and large cohort or registry studies
  • 2. Other priority research
  • 3. Standard articles

Only papers with a real abstract (at least 200 characters) are eligible for a summary. Everything else still appears as a linked headline, so nothing relevant is dropped.

RCT
RCT badge appears only for genuine randomised trials: either the publication type says so, or the abstract contains phrases such as "randomly assigned".
↑
Text fallback: if indexing hasn't caught up, phrases like "nationwide", "population-based" or "multicentre" in the abstract still mark a study as high priority.
≡
Headlines section lists every remaining paper with its journal and a link, so the email is complete without being long.
summarise_one() · OpenAI · strict JSON schema

An editorial note for each paper, held to its abstract

Each selected paper goes to an LLM (gpt-4o-mini, temperature 0.2), and the response must match a strict JSON schema. Free text isn't accepted, so every summary has the same shape and slots straight into the email template.

The prompt is written to keep the model faithful to the source:

  • Use only the abstract provided. If a detail is missing, write "Not reported".
  • Report effect sizes, CIs and p-values where they exist.
  • Different instructions for trials, meta-analyses, reviews and guidelines.
  • No hype words ("breakthrough", "game-changing").
{
  "name": "editorial_note",
  "strict": true,
  "schema": {
    "type": "object",
    "additionalProperties": false,
    "properties": {
      "study_type": { // RCT | Meta-analysis | … },
      "context":    { // the clinical question },
      "finding":    { // primary result + stats },
      "so_what":    { // why a clinician cares },
      "tags":       { "maxItems": 4 }
    },
    "required": ["study_type", "context",
      "finding", "so_what", "tags"]
  }
}
build_email_html() · Brevo API · Google Apps Script

Personalised delivery and a feedback loop

  • Subscribers come from a Google Sheet (filled by a sign-up form) and are filtered by specialty.
  • Each recipient gets an individually rendered HTML email, sent through the Brevo transactional API with rate-limited sends. Gmail SMTP is kept as a fallback.
  • One-click feedback ("Was this useful? Yes · No") goes to a Google Apps Script web app, which logs the vote to the sheet.
  • "Your Saves": papers a reader marked useful come back in their next issue, building a personal reading list.
  • Welcome emails go out automatically when someone subscribes.
⚙
Multi-specialty by config. Cardiology, General Practice and Spine Surgery all run on the same code. Adding a specialty means adding one JSON file (journals, MeSH terms, keywords, branding). No code changes are needed.
✓
Safe testing. --test-mode skips all state reads and writes, and --dry-run-email renders an HTML preview without sending anything.
⎋
Compliance. Subscribers opt in, every email has an unsubscribe link, and addresses are never shared.

What a summary looks like

Every summarised paper becomes a card with the same four fields. The card below is unedited model output from a real issue. Readers learn where to look, and the source abstract makes any claim easy to check.

RCTPCSK9 Inhibitors Prevention Diabetes
The New England Journal of Medicine · Bohula E, Marston N, Bhatia A

Evolocumab in Patients without a Previous Myocardial Infarction or Stroke

Context
This study examined whether evolocumab reduces the risk of major adverse cardiovascular events in patients with atherosclerosis or diabetes but without a previous myocardial infarction or stroke.
Finding
Evolocumab significantly reduced the risk of 3-point MACE (hazard ratio 0.75; 95% CI, 0.65 to 0.86; P<0.001) and 4-point MACE (hazard ratio 0.81; 95% CI, 0.73 to 0.89; P<0.001) compared to placebo over a median follow-up of 4.6 years, with no difference in safety events.
So what
Clinicians should consider PCSK9 inhibition with evolocumab to lower the risk of first cardiovascular events in patients with atherosclerosis or diabetes even if they have no prior myocardial infarction or stroke.

Engineering decisions

Built to be trusted, cheap to run and easy to audit

The system runs on its own with nobody watching, so I designed it for reliability and transparency first.

Deterministic rules before the LLM

Filtering and ranking use PubMed's own metadata in plain, testable Python. The model only writes summaries; it never decides what gets in.

Predictable, explainable and cheaper: the model never processes an editorial or letter.

Strict schema in place of free text

Structured outputs remove a whole class of failures: missing fields, chatty preambles and broken formatting all disappear. The template never has to guess.

With medical content, a consistent structure makes errors easy to spot.

State in git, not in a database

The PMIDs that have been seen or sent are stored as JSON and committed by the workflow. There's no infrastructure to maintain, and the commit history is a full delivery log.

The pipeline has run weekly since January 2026 with no server and no database.

Configuration over code

Journals, MeSH terms, keywords, branding and feedback flags are all set in a JSON config for each specialty. GP and Spine Surgery were added without touching the pipeline logic.

Covering a new specialty takes an afternoon, not a refactor.

What's in each issue?

Summaries of recently published cardiology research, key trial findings, brief clinical context for trainees and students, and links to the original journal articles. The content is educational and non-promotional.

How often, and to how many people?

Weekly, every Sunday. The list has fewer than 200 recipients and grows gradually through opt-in.

Why am I receiving this email?

Subscribers opted in through this website or were personally invited and confirmed their interest. No purchased, rented or third-party lists are used.

How do I unsubscribe?

Every email has an unsubscribe link, and requests take effect immediately. You can also reply to any issue to be removed.
